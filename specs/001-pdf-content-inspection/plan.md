# Implementation Plan: PDF Content Inspection

**Branch**: `001-pdf-content-inspection` | **Date**: 2026-10-20 | **Spec**: [spec.md](./spec.md)

**Input**: Feature specification from `/specs/001-pdf-content-inspection/spec.md`

## Summary

Reading what a document already contains, without changing it: for a page range, the distinct images
the pages paint, their annotations and resolved link targets, the interactive form, and the bookmark
outline; for a document, the embedded files it carries and the XMP packet byte-exact beside the values
parsed from it; and for indexing, one page's detail at a time through an iterator a caller can stop
early.

The approach is the one already in the tree, recorded so that later changes have a baseline. A single
read port in the domain is adapted by a stream-based port in the application layer and implemented in
the infrastructure layer by an engine that is one partial file per capability, returning immutable
domain read models. One payload rule — an inline budget of 256 KiB by default — decides whether bytes
travel inside a record or through a copy route to a caller-supplied stream. Damaged or unsupported
content is described through a warning whose kind names the cause instead of throwing; only a caller's
mistake or a file that is not a PDF raises.

## Technical Context

**Language/Version**: C# 14 on `net10.0` and C# 15 (`runtime-async=on`) on `net11.0`; both legs ship
in every package (`src/Directory.Build.props`).

**Primary Dependencies**: the BCL only in `SharpCorePDF.Domain`; `Microsoft.Extensions.*` only in
`SharpCorePDF.DependencyInjection`. No PDF engine, native library, platform-specific binary or runtime
package anywhere else.

**Storage**: none. Sources are file paths, streams or byte buffers, and the only thing written is the
`Stream` a caller hands to the copy route. No temporary file, no cache, no state between calls.

**Testing**: xUnit v3 4.0.0 on Microsoft.Testing.Platform 2.4.0 (Microsoft.NET.Test.Sdk 18.9.0,
coverlet.collector 10.0.1) over both legs. Fixtures are generated by `docs/tools/make-fixtures.py`,
stay binary in Git, and are validated out of band by `docs/tools/validate-pdf.py`.

**Target Platform**: cross-platform class libraries; no native or platform-specific dependency, so the
packages carry no deployment prerequisite.

**Project Type**: library — four layered packages plus the `SharpCorePDF` meta-package, consumed by an
application that supplies its own I/O.

**Performance Goals**: a page enumeration holds one page's records at a time, so indexing 200 pages
costs the pages consumed rather than the document; a payload copy runs through a bounded buffer so the
peak working set stays flat across 1 MB, 10 MB and 50 MB payloads. Allocations, wall time and retained
heap are recorded in `docs/measurements.md` and read against its budgets.

**Constraints**: read-only — no source is modified or disposed, and no destination is opened that the
caller did not supply; page numbers are one-based and inclusive; orderings, identifiers, bytes and
warning sets are identical across reads and runs; both legs build with zero warnings, `RS0016` and
`RS0017` are build errors, and new code is held to the 90% coverage condition; nothing opens a socket,
writes a log or keeps a password.

**Scale/Scope**: up to 100 000 pages and 512 MiB per source by default (`MaxPagesPerSource`,
`MaxSourceBytes`); payloads from one byte to 50 MiB exercised; a 200-page indexing fixture; seven
capabilities over six read-model families.

**Structure Decision**: the feature extends the four layers that already exist rather than adding a
project. Callers see one port in `SharpCorePDF.Domain`; the engine implements the stream-based
`SharpCorePDF.Application` port so it never has to know how a document was addressed; the
`SharpCorePDF.Application` service turns an `IPdfContentSource` into that stream. Read models live in
the domain because they are the vocabulary of the answer, not the mechanism of producing it, which is
what keeps `SharpCorePDF.Domain` free of PDF syntax. The engine is split by capability — images,
annotations, form, outline, metadata, page detail — because those share the page-tree walk, resource
resolution and stream decoding but little else; a single file would be a thousand lines with no seam.

## Complexity Tracking

No entries. The feature adds no project, no package reference, no target framework, no native
dependency and no fourth layer. Two shapes a reviewer might query are deliberate:

| Shape | Why it is not complexity to track | The simpler alternative fails because |
| --- | --- | --- |
| Two ports (`IPdfContentReader` in Domain, `IPdfPageContentReader` in Application) | It is the existing layering applied once: the caller port takes a source, the engine port takes a stream | A single Domain port taking a `Stream` either exposes I/O to the domain or makes the engine open files itself, which breaks Principle II |
| One partial reader file per capability | Each file is a capability with its own tests; the shared walk stays in the core file | A single class of roughly 1 300 lines has no seam for review, and every capability change would touch the same file |

## Risks and Mitigations

- **The source is read into memory once.** A read holds the document's bytes (bounded by
  `MaxSourceBytes`), so "only the pages of the range are read" is a statement about parsing, decoding
  and record construction, not about I/O. The specification is worded that way on purpose, and the
  quickstart states it, so a caller does not infer constant memory from a large file.
- **Identifiers are identifiers of a read.** `inline:3:2` and the suffixed embedded-file names are
  stable for the same bytes but are not document identity; the read model says so and the
  specification lists it as an assumption.
- **The API snapshot is unreleased.** Every member is in `PublicAPI.Unshipped.txt`; promoting an entry
  to `Shipped` before the release that ships it would claim a surface no package carries.
- **Coverage is judged by Sonar, not locally.** The 90% condition is on new code, so a local
  `dotnet-coverage collect` run is an estimate; the quality gate is the evidence.
- **Fixtures are written by the tests** (`PdfContentFixtures`), so the binary corpus in
  `tests/SharpCorePDF.Tests/Assets` does not grow and no cross-reference offset moves in Git.
