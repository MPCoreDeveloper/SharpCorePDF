# 25. How This Manual Is Built

This manual is produced by the library it documents. The chapters are Markdown files in
`docs/manual/src`; the PDF beside them is generated by a console tool in `tools/SharpCorePDF.Manual`,
which you can build and run yourself, and no page is typeset by hand. The tool is not packed with the
library: it is a maintainer utility, and it is described here because its output is the book you are
reading, and because almost everything it does is an application of the surface the earlier chapters
describe.

Two facts shape the design. The only third-party part of the build is a browser, and the browser does
one thing only: it turns HTML into laid-out pages. Everything that has to know what a PDF *is* — the
running footer, the outline, the metadata, and reading the printed file back to measure it — is
SharpCorePDF. The builder this replaced needed Python with `markdown`, `pygments` and `pypdf` for the
same book; this one needs neither Python nor a PDF package other than this one.

## The four stages

| Stage | Reads | Writes | Done by |
| --- | --- | --- | --- |
| Markdown to HTML | `docs/manual/src/*.md`, `manual.css` | one HTML document | `MarkdownConverter`, `SyntaxHighlighter`, `ManualHtml` |
| HTML to pages | the HTML document | a printed PDF | Chrome or Edge, headless |
| Measure | the printed PDF | the page of every heading | `PageIndex` over `PdfContentReaderService` |
| Finish | the printed PDF and the measurements | the final PDF | `ManualFinisher` over `PdfEditPlan` |

Each stage is one file, and each can be stopped so that you can look at what it produced: `--keep-html`
leaves the generated HTML on disk, and `--no-stamp` writes the printed file with neither footer nor
outline nor metadata.

## Markdown to HTML

The converter understands the subset the chapters use and refuses the rest rather than guessing: ATX
headings, fenced code with a language, pipe tables, single-line blockquotes, flat lists, inline code,
bold, italic, links and horizontal rules. A chapter holds no raw HTML, no nested list and no image, so
there is no code for them, and a table is taken as written — this book has no column alignment to
interpret. That is a deliberate limit: a converter written for one book is easier to keep correct than
a general one, and the chapters are held to it.

Code fences are highlighted into class names, not inline colours — `k` for a keyword, `s` for a string,
`c` for a comment, `m` for a number, `n` for a name, `p` for punctuation. Those names are the ones the
stylesheet has always styled, which makes the highlighting a contract between the highlighter and the
CSS rather than a picture baked into the text: the same book can be restyled without passing the tokens
through anything again. C#, shell, PowerShell and JSON have rule sets; any other fence is escaped and
printed without colour, with its language as the label above the block.

Every heading gets an anchor that is unique in the book, not only in its chapter. Two chapters that
both contain a section called "Overview" get distinct ids, because the contents page and the outline
address a heading by its anchor, and a duplicate would send both links to the first one.

## The browser lays out, and nothing else

Chrome is started headless with a throwaway profile, and the flag that matters most is
`--no-pdf-header-footer`:

```powershell
chrome.exe --headless=new --disable-gpu --disable-extensions --no-pdf-header-footer `
  --run-all-compositor-stages-before-draw --virtual-time-budget=20000 `
  --user-data-dir=<temporary profile> --print-to-pdf=docs\manual\build\pass1.pdf `
  file:///<root>/docs/manual/build/manual.html
```

The browser's own header and footer would print the file URL on one side and the date on the other,
which is not what a book carries, and its counter cannot write "Page 7 of 118" in the typeface the
stylesheet chose. They are off, and the footer is written afterwards by SharpCorePDF.
`--run-all-compositor-stages-before-draw` makes sure the paint that is captured is the final one, and
`--virtual-time-budget` gives the layout time to settle before the capture, which matters at this size.

The document is loaded from a `file://` URI, not from a web server, so the stylesheet and the cover logo
are read from the repository and the build needs no network. Nothing else about the machine matters: the
browser's profile is created inside the build directory and removed after the print.

## Measuring the contents

A page number is not known until the page exists, so the first pass prints a middle dot where each
number will go. The printed file is then read back, and every heading is located in the text of the
pages:

```csharp
var probe = await PageIndex.ReadAsync(new PdfByteArraySource(printed, "pass1.pdf"), cancellationToken);

var (pages, _) = PageIndex.Locate(probe.Pages, headings, firstBodyPage);
```

`probe.Pages` holds the whitespace-collapsed text of each page, one string per page. A heading is
located by searching forward from the page of the previous heading, and the search starts on the first
page after the contents. The two rules do different jobs: searching forward stops a repeated section
title from pulling the cursor back into an earlier chapter, and starting after the contents stops a
contents row from matching the page it is itself printed on.

The second pass prints the measured numbers. The finished file is then read once more, because a wider
row could push a heading to the next page and make the numbers that were just printed stale. The page
column is right-aligned with tabular figures and a minimum width, so in practice nothing moves, but the
check is cheap: if the measurements changed, the pass is repeated with them, at most twice.

## The footer, the outline and the metadata

The last stage is the one that needs a PDF engine, and it is the reason the build is written in C#. For
every page from the second onwards a one-page overlay is drawn with `PdfDocumentBuilder` — a rule, a
title on the left, "Page N of M" on the right, in Helvetica 8 point — and composited over the page with
`PdfEditPlan.Overlay`, the operation Chapter 14 describes:

```csharp
var plan = PdfEditPlan.Create();

for (var page = 2; page <= info.PageCount; page++)
{
    var overlay = FooterOverlay(info.Pages[page - 1].Size, page, info.PageCount);
    plan = plan.Overlay(new PdfByteArraySource(overlay, $"footer-{page}.pdf"), page);
}

plan = plan.SetOutline(outline).SetMetadata(metadata);

var editor = new PdfDocumentEditorService(
    new PdfDocumentReader(PdfEngineOptions.Default),
    new PdfEditEngine(PdfEngineOptions.Default));

var finished = await editor.ApplyToArrayAsync(source, plan, cancellationToken: cancellationToken);
```

The cover carries no footer, exactly as page 1 of a book. The footer lives inside the 18mm bottom margin
the stylesheet declares; `PdfTypeface.Measure` gives the width of "Page 7 of 118" so the right-hand run
ends at the margin instead of drifting, and the two runs are drawn in the muted purple of the book's
structure over a hairline of the same hue. One read, one write: the overlay, the outline and the
metadata are one plan, so the file is opened once and closed once.

A detail is worth stating because it is easy to get wrong, and because it is the kind of thing a
screenshot hides. The canvas an authored page is drawn on counts `y` downwards from the top-left corner,
while the page it becomes counts upwards from the bottom-left one; `PdfDocumentBuilder` converts between
them for you, which is what lets a page be written in layout coordinates. The footer, however, is
defined against the bottom edge, so its baseline is `page.HeightPoints - 30`. Anchor it at `30` and the
running footer is printed below the top edge of every page, where it reads as a header. The first build
of this tool did exactly that, and it was found by decompressing a page's content stream and reading the
text matrix — not by looking at the page, where a footer at the top is easy to mistake for a header the
stylesheet meant.

The second half of that fault was not in this tool at all. Chromium writes the page it prints with a
transform stated outside a `q` — `.24 0 0 -.24 0 841.92 cm`, which maps its own layout onto the page —
and the streams of a page reach a reader as one stream, so the transform was still in force where the
overlay was drawn. The footer came out at a quarter of its size, pressed into the top-left corner, where
it reads as a short dash of purple above the first line. `PdfEditPlan.Overlay` now frames the original
content in `q`/`Q` whenever it draws a layer, so a statement a page leaves open cannot reach what the
plan draws after it, and the bytes of the page are still the bytes that were read. Neither fault was
visible in a screenshot until the page was measured: a squashed footer looks like a rule, and a footer at
the top looks like a header.

The outline is built from the same heading list the contents uses, so a bookmark and a contents row
cannot disagree about either the text or the page: both are the heading, and the number measured for it.
An `##` becomes a child of the `#` above it, which is why the bookmarks open as a tree in a reader's
sidebar. A second list to keep in step was never an option; there is one list, and the contents and the
outline are two renderings of it. The metadata — title, author, subject, keywords, creator and producer
— is set in the same plan. The creator names the stages ("markdown + Chromium + SharpCorePDF"); the
producer names the library, because the bytes were last written by it.

## What the build does not do

- It does not convert the result to PDF/A. The manual is an ordinary PDF 1.7 file, and Chapter 24
  explains what converting it would add and what it would refuse.
- It does not check the prose. A chapter that states a wrong page count builds happily and prints the
  wrong number.
- It does not run in CI. The tool is compiled with the rest of the solution, but the book is generated on
  a machine with a browser, before a release, and the release records the page count it produced.
- It does not publish the HTML. GitHub renders the Markdown chapters directly and the PDF is the
  artifact; the generated HTML is an intermediate file, kept only when `--keep-html` asks for it.
- It is not a general Markdown library. Nothing in it is shaped for another document: a feature this
  book does not need is a feature the tool does not have, which is why it stays readable.

## Running it

```powershell
dotnet run --project .\tools\SharpCorePDF.Manual                   # writes docs/SharpCorePDF-Manual-<version>.pdf
dotnet run --project .\tools\SharpCorePDF.Manual -- --keep-html    # also keeps the generated HTML
dotnet run --project .\tools\SharpCorePDF.Manual -- --no-stamp     # stops after the browser printed
```

Chrome or Edge is the only prerequisite beyond the .NET SDK. `SHARPCOREPDF_CHROME` points the printer at
a browser installed somewhere else, and the build fails with a message that says so rather than with a
stack trace. The run prints what it did — chapters, headings, pages, bookmarks, and whether the footer
was found on page 2 by reading the finished file back — and it exits with a non-zero code when the
footer is missing, so a build that silently lost its finishing pass cannot be mistaken for a good one.

| Argument | What it changes |
| --- | --- |
| `--root <path>` | the repository root; found from the tool's location when it is not given |
| `--out <path>` | the file to write; `docs/SharpCorePDF-Manual-<version>.pdf` by default |
| `--version <x.y.z>` | the edition the cover, the footer and the metadata state |
| `--keep-html` | keep the generated HTML in `docs/manual/build` |
| `--no-stamp` | skip the footer, the outline and the metadata |

That is the whole build: a converter that knows the subset of Markdown this book uses, a browser that
lays the pages out, and this library for everything that turns printed pages into a book — a footer on
every page but the first, a contents page whose numbers were measured from the file you are holding,
bookmarks that agree with it, and the metadata a reader shows in its title bar. None of it is a separate
engine, which is the point: the manual is a document this library produced, and the code that produced
it is in the repository next to the code it describes.
