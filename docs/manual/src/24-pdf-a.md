# 24. Archival PDF (PDF/A)

PDF/A is a set of structural rules for documents that must still open in decades. Writing for a profile
means writing the structures those rules name — a stated version, an XMP identification of the profile, an
output intent, the program of every font, no encryption — and removing or refusing what the profile
forbids.

It does not mean the library can tell you the file conforms. That answer comes from a validator, and this
release keeps the two apart on purpose:

- the writer writes the structures and refuses what it cannot write correctly;
- veraPDF, an independent implementation, decides whether the result conforms;
- `IsWritten = true` says "the structures are there", never "this is a PDF/A document".

## Writing an archival document

```csharp
using SharpCorePDF.Domain.ValueObjects;
using SharpCorePDF.Domain.Ports;

using var destination = File.Create("archive-2b.pdf");

var result = await archiveWriter.ConvertAsync(
    new PdfFileSource("statement.pdf"),
    destination,
    PdfAProfile.PdfA2B,
    new PdfAConversionOptions
    {
        ModificationDate = new DateTimeOffset(2026, 1, 1, 0, 0, 0, TimeSpan.Zero),
        DocumentId = "00112233445566778899AABBCCDDEEFF",
    });

if (!result.IsWritten)
{
    foreach (var requirement in result.UnsatisfiedRequirements)
    {
        Console.WriteLine(requirement);
    }
}
```

`archiveWriter` is an `IPdfAWriter`, registered by `AddSharpCorePDF()` and constructible by hand as
`new PdfAWriterService(new PdfAWriter())` (Chapter 10). The source is opened, read to its end and disposed;
the destination belongs to the caller and is flushed, not closed.

`PdfAProfile` names five profiles — three at level B and two at level U:

| Profile | Part of ISO 19005 | Level | PDF version written | Transparency | JPEG 2000 | Embedded files |
| --- | --- | --- | --- | --- | --- | --- |
| `PdfA1B` | 19005-1 | B | 1.4 | refused | refused | refused |
| `PdfA2B` | 19005-2 | B | 1.7 | allowed | allowed | refused |
| `PdfA2U` | 19005-2 | U | 1.7 | allowed | allowed | refused |
| `PdfA3B` | 19005-3 | B | 1.7 | allowed | allowed | allowed |
| `PdfA3U` | 19005-3 | U | 1.7 | allowed | allowed | allowed |

Level B keeps the visual appearance. Level U adds one requirement: every glyph the document draws has a
Unicode equivalent, which is what a text extractor or a search index reads. The writer already states a
`ToUnicode` map for every font it subsets, so a document that converts to `PdfA2B` converts to `PdfA2U`
as well; the level is written as `pdfaid:conformance` in the packet, and nothing else about the file
changes. A profile at level A — tagged structure, accessibility — is not offered, and PDF/UA is a
different standard.

The profile decides the version of the file, whatever `PdfVersion` a caller might otherwise have asked
for; a PDF/A-1b document that claims 1.7 is not one.

`PdfAConversionOptions` carries the document information, the identity of the result and the output
intent, nothing else. A fixed `ModificationDate` and `DocumentId` make two conversions of the same source
byte-identical, which is what a test that compares files needs.

## What the writer writes

- **The header version** the profile names, 1.4 or 1.7.
- **An XMP packet** in the catalog, uncompressed and UTF-8, carrying `pdfaid:part` and
  `pdfaid:conformance`, plus the document information mirrored into `dc:title`, `dc:creator`,
  `dc:description`, `pdf:Keywords`, `pdf:Producer`, `xmp:CreatorTool` and the two dates. A profile
  requires the dictionary and the packet to agree, so the same values are written to both.
- **An output intent** in the catalog: `/S /GTS_PDFA1` and a destination profile. By default the profile is
  sRGB generated by the library — a complete ICC v2 program, the same bytes on every platform — so nothing
  has to be shipped as an asset or licensed. A caller that archives for print supplies
  `PdfAConversionOptions.OutputIntent` instead: the bytes, the component count and the condition it names are
  written as given, and the library does not convert the pages into that colour space. The intent is checked
  as an ICC profile first — declared length, the `acsp` signature, and a data colour space that agrees with
  the component count — because a broken profile produces a file that looks archival and is not.
- **`/NeedAppearances false`** on the form, when the source has one: a conformance reader must be able to
  paint the form without building appearances itself.
- **An association for every embedded file**, when the profile is PDF/A-3b: the catalog carries an `/AF`
  array, each entry of the `EmbeddedFiles` name tree and its association name the same file specification
  object, and every specification states an `/AFRelationship`. A file that already states one keeps it — the
  source's claim is evidence this writer does not have; one that states none takes
  `PdfAConversionOptions.AssociatedFileRelationship`, which defaults to `/Unspecified` rather than inventing
  a meaning.
- **No encryption.** See below.

Everything else is copied: page content, images, fonts and their programs are written byte for byte, and
the page tree is flattened the same way an edit flattens it.

## What is removed, and what is refused

Two different things can stand between a source and a profile, and they are treated differently.

**Removed, with a warning of kind `PdfAFeatureRemoved`**: things whose absence changes no page.

| Removed | Why it is safe |
| --- | --- |
| The JavaScript name tree of the catalog | A viewer may not run it in an archival document anyway. |
| A catalog open action that runs JavaScript | The document opens without running anything. |
| The `/NeedAppearances` flag | The appearances must be in the file, not built by the reader. |
| Custom document information entries | They have no XMP property without an extension schema. |
| The XMP packet and output intent of the source | Replaced by the ones the profile requires. |

**Refused, with `IsWritten = false` and a named requirement**: things that cannot be repaired without
changing what a page looks like, or that are data.

| Refused | Why |
| --- | --- |
| A font that is not embedded | There is no program to embed. Standard fonts have none; supply a TrueType face (Chapter 12). |
| A CID font subset without `/CIDSet`, for 1b | ISO 19005-1 requires the set, and the writer cannot know which CIDs a program it did not subset describes. |
| Transparency for 1b — a soft mask, a blend mode, a transparency group | PDF 1.4 has no transparency, and making it opaque changes the page. |
| `JPXDecode` or `LZWDecode` for 1b | The first part of ISO 19005 forbids both filters. |
| Embedded files for 1b and 2b | Only PDF/A-3 allows attachments. |
| Optional content for 1b | PDF 1.4 has no layers. |
| An annotation without an appearance stream (except `Link` and `Popup`) | A viewer would have to invent the content. |
| A JavaScript, `Launch`, `Sound`, `Movie`, `Rendition`, `ImportData` or `SubmitForm` action | The profile forbids the action itself, not just its startup use. |
| An external file stream (`/F`) | The document must contain what it displays. |

A refusal writes nothing to the destination, so a caller that ignores `IsWritten` does not get a file it
might ship by mistake:

```text
PDF/A-2b: nothing written, 1 unsatisfied requirement(s)
the font 'Helvetica' is not embedded; a PDF/A document must carry the program of every font it uses.
```

Every conversion that does write adds a `PdfAProfileWritten` warning naming the profile and stating that
conformance is established by an external validator.

## Archival edits

An edit can target a profile, which is what an archive wants when it has to fix one page of a master:

```csharp
using SharpCorePDF.Domain.Aggregates;
using SharpCorePDF.Domain.ValueObjects;

var plan = PdfEditPlan.Create(PdfEditOutputOptions.Default with
{
    PdfAProfile = PdfAProfile.PdfA2B,
    TargetVersion = PdfVersion.V1_7,
    ModificationDate = new DateTimeOffset(2026, 1, 1, 0, 0, 0, TimeSpan.Zero),
});

await editor.ApplyAsync(new PdfFileSource("statement.pdf"), plan, destination);
```

The same analysis runs, and an edit that cannot be made conformant is refused with a
`PdfEditPlanValidationException` whose errors name every requirement — before the writer opens the
destination. `PdfEditResult.OutputVersion` reports the version the profile wrote.

A profile and encryption cannot both be written: `PdfEditOutputOptions.Validate()` reports the conflict and
executing such a plan throws before the source is read, because ISO 19005 requires an archival document to
be readable without a password. An edit that is not archival may be encrypted; `PdfEditOutputOptions.
Encryption` writes AES by default and the writer reads its own output back with that password when
`VerifyOutput` is on.

## Evidence

Conformance is not a claim this library makes about itself, so the release is checked with veraPDF:

```powershell
python docs/tools/validate-pdfa.py --profile 2b archive-2b.pdf
python docs/tools/validate-pdfa.py archive-1b.pdf archive-3b.pdf
```

The tool finds veraPDF on `PATH`, through `VERAPDF_HOME`, or with `--verapdf`, and needs a Java runtime;
`--profile` states the flavour, and without it veraPDF detects the flavour the document declares. It exits
0 when every file passes, 1 when one fails, and 2 when it cannot run at all. `--require-version` refuses a
validator older than the one CI pins, and `--format xml --report-dir <dir>` takes the verdict from the
machine-readable report and keeps that report beside the run.

`compliance.yml` runs the whole check on every push, on every pull request and once a week: it installs the
pinned veraPDF, writes both sets of documents, validates each against the profile it was written for and
uploads the reports. The weekly run is what turns a validator upgrade that changes the answer into a red
build, in a week when this library did not change a byte.

Agreement between implementations is a stronger statement than one PASS, so `validate-pdfa-cross.py` reads
the same files with two more. Apache PDFBox preflight shares no code with veraPDF and validates PDF/A-1 on
its own: for `1b` its verdict is a second opinion, and for `2b` and `3b` it is asked only to parse the file,
which the tool reports as `parsed` and never as a verdict, because PDFBox 3.0 does not implement those
profiles. Ghostscript is the third: it rewrites the document as archival output from what it understood,
which proves the file is not readable only by the tool that wrote it. `compliance.yml` passes
`--strict-tools`, so an implementation that is missing fails the run instead of quietly narrowing it.

The `archive-pdfa` scenario of `examples/SharpCorePDF.Examples` writes `archive-1b.pdf`, `archive-2b.pdf`
and `archive-3b.pdf` from one authored page, and refuses a page set in Helvetica. With
`SCPDF_ARCHIVE_SOURCE` naming a document, it archives that document for all three profiles as well, which
is how a real file reaches the check. On 2026-11-13, with veraPDF 1.30.4, all six files — the authored page
and a six-page document written by "Microsoft: Print To PDF" — reported `PASS`, and `docs/parity.md`
records the run; the earlier 1.30.3 run on 2026-10-22 covered the same profiles the same way. A document
whose `Text` annotation carries no appearance stream was refused rather than written, which is the intended
behaviour.

The `sign-and-archive` scenario signs what it archived: one authored page written as PDF/A-3b, and then a
signature appended to that file (Chapter 23). The order is what makes both promises hold at once — the
conversion writes the archival structures, and the signer adds a revision after them rather than rewriting
anything — so a validator reads the same structures the conversion wrote, and the signature covers the whole
file. Its certificate is made for the run and never written down, which is why the artifact can be produced
without a key in the repository.

## What this is not

- It is not a validator, and it does not report "PDF/A compliant".
- It is not PDF/UA or PDF/X.
- It does not fetch an ICC profile. It writes either the sRGB program it builds or the bytes the caller
  supplies, and it converts no page into that colour space: a CMYK intent on a document that paints in
  device RGB is a mismatch a validator reports, not something the library resolves.
- It does not generate missing appearance streams, so a document whose widgets or notes have none is
  refused rather than silently filled in.
