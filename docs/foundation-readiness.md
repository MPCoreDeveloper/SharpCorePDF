# .NET Foundation readiness

The .NET Foundation's [eligibility criteria](https://github.com/dotnet-foundation/projects#eligibility-criteria)
taken seriously as a description of a healthy project, rather than as a form to fill in. This document
maps every criterion to a repository artifact, names the gap where there is one, and records the
decisions only the owner can make.

`docs/release-checklist.md` is the sibling document: it gates a version of the package, this one gates
the project's public posture. `docs/foundation-application.md` is the third and the last: it holds the
gate that decides *when* an application is filed, and the answers that go into it.

## Verdict, 2026-10-17

**Eligibility: passes on paper — and since 2026-10-17 the three documents the criteria name exist at the
repository root, with a `NOTICE` beside them that states who holds the copyright and what third-party
material exists. Activity: thin, and honestly so.**

The Foundation evaluates the two separately, and its own application form says what happens in exactly
this case:

> A project that passes Eligibility but hasn't yet built Activity is onboarded at the **Seed** level
> rather than rejected, and is automatically re-evaluated each quarter — so applying early is never a
> dead end.

So an application today would not be refused; it would be filed under Seed, which is a reasonable place
for a library that has never published a package. The same form suggests, without making it a gate,
that a pre-traction project gets more value from the [Foundation Discord](https://discord.gg/dotnet-foundation)
first — because stars, forks and outside issues are what the committee reads as evidence of a community.

## The five decisions only the owner can make

Two of the five were answered on 2026-10-17 and are recorded here as decisions rather than as notes. The
three that remain are the ones that need a legal answer or a person's signature.

1. **The package id** — **answered 2026-10-17: it stays, and `SharpCorePDF` itself is claimed first.**
   The transposition away from `PdfSharpCore` is real, and the response is not to rename but to publish the
   product's name as an entry point: `SharpCorePDF` is a meta-package that depends on the four layers, so a
   consumer types the name they already know instead of working out which of four layer names a merge
   needs. `NOTICE` states the non-affiliation in one paragraph; `docs/release-checklist.md` G0 holds the
   reasoning and the two consequences for the first push.
2. **Contribution model or Assignment model** — the Foundation offers both. Assignment transfers
   ownership of the project's intellectual property and grants a licence back; contribution keeps the
   copyright and grants the Foundation a broad licence. The second is what most libraries assume, but it
   is a decision, not a formality.
3. **Trademarks: Licensed or Disclaimed** — the CLA defaults to *Licensed*: the project keeps the
   trademark and licenses the Foundation to use it. A name that resembles another product's makes this
   conversation longer whichever option is chosen.
4. **The signatories** — the top one to five contributors, with contact addresses, because the CLA goes
   out through DocuSign. Today that list has one name on it.
5. **Which account holds the project afterwards** — **answered 2026-10-17: the personal account stays.**
   An Organization would be a structure with a single member and no second public face to put behind it
   (the maintainer's other work is private), so the project is filed and administered as a User account.
   The consequence to keep in mind is that the nuget.org trusted publishing policy is owned by that
   personal account, and the bus factor in the verdict below stays at one until a second committer exists.

## The process, from the Foundation's side

1. **Application** — a public issue from the template, eight sections. Section 6 ("why are you
   applying") is the only required free-text answer.
2. **Review** — the Project Committee reads it and follows up with questions; the questionnaire then
   goes to the Board with a recommendation.
3. **Board vote** — the Board meets monthly, which is the only fixed delay in the process.
4. **CLA** — DocuSign, all signatories, with the trademark choice recorded.
5. **Onboarding** — a checklist: CLA bot, project-leader mailing list and Slack, licence moved to MIT
   (already MIT), the Code of Conduct added to the README, the project list on the Foundation site,
   project layout, README and website updates.
6. **Re-evaluation** — quarterly, which is why Seed membership is worth having rather than waiting.

## When an application is filed

The owner's decision, taken 2026-10-17: **the application is filed as soon as the eight conditions in
[`docs/foundation-application.md`](foundation-application.md) are all true** — not before, and not "someday".
That document holds the checklist, the state of each condition, and the answers to the form, so that filing
costs an hour rather than a week of reconstruction.

As of this date three conditions are true (the three documents exist) and five are not: nothing is
published on nuget.org, so no stable release has aged 90 days either; no outside contribution exists;
Discussions is off; and three of the five decisions below are unanswered — the package id and the account
shape were decided on 2026-10-17. Two of the false conditions cost nothing but a settings toggle, and
neither needs anybody else's time: **GitHub Discussions**, and **private vulnerability reporting**, without
which the first channel in `SECURITY.md` does not resolve.

## What to do now, in the order that also serves the release

None of the following is speculative work for an application. Every item is something the first consumer
needs whether or not an application is ever filed:

1. **`CHANGELOG.md`** — **done, 2026-10-17.** Keep a Changelog format, an `[Unreleased]` entry that states
   what the tree contains and what it deliberately does not, and the honest opening that no version has
   been published. It is G3 in `docs/release-checklist.md`, and from here it is kept current in the commit
   that bumps `<Version>`.
2. **`SECURITY.md`** — **done, 2026-10-17.** Scope, two private channels (no address to publish), a 7-day
   acknowledgement, and a safe-harbour paragraph, because a project that parses untrusted bytes should say
   what it wants reported.
3. **`CODE_OF_CONDUCT.md`** — **done, 2026-10-17.** Contributor Covenant 2.1 verbatim, with the
   `[INSERT CONTACT METHOD]` replaced by two real channels: the criterion is "adheres to, *and enforces*",
   and an unenforceable contact line is where most projects fail it.
4. **`CONTRIBUTING.md`** — **done, 2026-10-17.** The two SDKs and the per-framework test invocations, the
   bar a change clears (a test that fails when reverted, the API snapshot in the same commit, zero
   warnings), and the published ladder from contributor to committer.
5. **Enable GitHub Discussions** — the cheapest public communication channel available, and the one a
   NuGet consumer already has an account for. It is condition 3, and `CONTRIBUTING.md` promises to reword
   itself on the day it happens.
6. **Dependabot alerts, or CodeQL** — the half of "high priority on producing secure software" that a
   document cannot supply. A policy describes the process; a scanner watches the dependencies.
   **Partly done, 2026-10-17:** `.github/dependabot.yml` schedules version updates for the NuGet packages
   and the workflow actions, with the project folders listed one by one because the updater does not read
   a `.slnx`. Alerts and *security* updates are still a repository setting (Settings → Code security), and
   no file in this repository can switch them on.

## What not to do

- **Do not file the application to manufacture legitimacy.** Activity is measured, and a package with
  no downloads does not become a community because an issue was opened.
- **Do not cite the planning chain.** `_bmad-output/` is gitignored, so the PRD, the epics and the
  architecture spine are not public documentation; a reviewer who follows the links finds nothing.
- **Do not claim a differentiator without its caveat** — the README and `docs/measurements.md` already
  state what is measured and what is not, and that habit is itself one of the criteria ("open and
  honest about the quality of its code").
